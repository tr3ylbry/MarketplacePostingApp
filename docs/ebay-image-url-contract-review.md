# Sandbox image URLs: evidence review and proposed limited contract

Reviewed offline on November 22, 2026. This is a **decision package, not an approved URL contract, downloader or admission implementation**. Stage 9B remains In Progress. Inventory policy/writes, normal EPS transport and real receipt/association admission are unchanged and disabled.

The separately authorized [offline prototype](ebay-offline-image-egress-prototype.md) now models Option B with invented responses and mock ports only. Its restrictions remain application proposals; no real URL, classifier, resolver, socket, persistence or admission implementation is supplied. The next review is of that prototype, not permission for a live experiment.

## Recommendation and evidence boundary

Recommend **B: an exact response-returned image URL, held only in bounded operation-local memory for one separately authorized verification**. Its query can remain opaque. An exact approved origin, response provenance and enforceable egress/resource controls can constrain the application's use without knowing parameter names or inventing signature semantics. This is a deliberately limited application policy, not a claim to recognize every valid eBay URL.

Current evidence supports designing and testing that policy offline. It does **not** establish a final real receipt validator, downloadable pixels, Inventory ingestion, remote ownership, recovery or erasure. Keep the current rejection/admission boundary until a later implementation is independently reviewed and a distinct experiment is approved.

One completed capture-only experiment consumed its entire budget: one authorization-code exchange, one authenticated GetUser and one image-create POST. The response was HTTP 201 with bounded JSON-object evidence and no duplicate headers observed. No returned URL was fetched. Its attempt remains **unknown/unassociated**, with permanent source/derivative fences, one structural report and no receipt/association. Full returned URLs, path contents, resource IDs and query names/values were deliberately not retained. The old URLs cannot be recovered or reconstructed from this report.

Evidence used here:

- **O — observation:** the retained, sanitized capture summary. Private execution identifiers, correspondence and operational details stay in private records.
- **S — retained source:** the [existing source review](ebay-real-media-design.md#evidence-and-current-boundary), including its dated Media OpenAPI/image-guidance excerpts and retained human-support summary. These support field roles, multipart creation, 201/Location and possible EPS processing. No external document or support thread was refreshed for this review; an excerpt/summary is not a newly verified complete provider contract.
- **C — current code:** [structural parser](../src/application/ebayCaptureReport.ts), [pinned capture client](../src/infrastructure/ebay/captureClient.ts), [closed admission](../src/infrastructure/ebay/realMediaEvidence.ts), and [capture SQL](../drizzle/0011_sandbox_image_capture.sql).
- **P — proposal:** a deliberately conservative application decision requiring separate approval. Application budgets below are not confirmed eBay limits.
- **U — unresolved:** information these sources do not establish. No DNS, host resolution, requests, private configuration, database or service access was used for this review.

## Why the normalized report is not a final validator

The current parser rejects raw backslashes, non-visible ASCII and strings over 8,192 characters before reporting a URL. It is intentionally a redactor, not an origin/identity validator. Its `valid` flag accepts syntactic HTTP(S), not a trusted endpoint. It stores no raw URL.

Eight pure in-memory checks using invented `.invalid.test` strings and the existing parser passed, with networking blocked. They confirmed default `:443` disappears from the port flag; empty `@` can yield a false user-info flag; encoded dot segments can disappear before segment counting; host case is normalized; a retained encoded path segment is flagged; different query contents can yield identical reports; raw backslashes and raw newline are rejected. These checks demonstrate information loss and legitimate parser behavior, not a finding that the capture parser should retain secrets or admit real URLs. They make no request and reconstruct no experimental URL.

## Proposed controls for a later primary-only verification

All controls in this section are proposals. No downloader or schema change is made here.

### Raw URL, origin and unchanged transmission

- Candidate origin: exactly `https://i.sandbox.ebayimg.com`, TLS port **443**. No wildcard, suffix match, trailing-dot alias, IP literal, alternate hostname, HTTP or Production fallback. Location is never a download destination. Approve each field/host separately.
- Take one exact primary `imageUrl` string only from a fresh, duplicate-free, bounded 201 response bound to the intended owner/session/seller/connection/grant/configuration/source/derivative/attempt. No submitted URL, report reconstruction, derived path, guessed maximum variant or serialized “trusted” boolean.
- Proposed raw limit: 8,192 visible ASCII bytes, no controls/DEL/whitespace, backslashes, user-info syntax including empty `@`, or fragments including empty `#`. Require exact lowercase HTTPS authority with **no raw explicit port**; effective 443 only. Rejecting even literal `:443` is a conservative trial choice, not an observation about the lost response. If the future raw response violates it, stop for review rather than normalize it silently.
- Check raw syntax before WHATWG parsing. Require parsed origin/host/scheme plus exact serialized `href === raw`; reject transformations instead of claiming universal canonical equivalence. Bound the path to at most 16 nonempty segments and 512 raw bytes per segment, solely as trial budgets. No inferred segment count, prefix, extension or identifier alphabet from the observation.
- Reject raw dot segments, doubled path separators, malformed percent triplets, encoded path separators/backslashes/dot/control/delimiter bytes and nested path escapes. For queries, preserve the exact opaque substring: no URLSearchParams, decoding/re-encoding, sorting, duplicate-key folding, dropping parameters, converting `+`, or appending data. Validate percent-triplet framing and forbid encoded controls/backslashes, but do not decode query values into URLs/identifiers or assign signature semantics. Opaque encoded query delimiters are data, never a second application parsing channel. Exact rejection vectors need offline review, particularly before accepting any nested escape.
- Keep and send the original validated request-target bytes, including query order, case and delimiters. An HTTP library that silently rewrites them is unsuitable until exact transmission is demonstrated with synthetic inputs. Equality under one parser does not alone prove on-wire identity or provider interpretation.

### Provenance, DNS, socket and HTTP

- Use a non-serializable, one-operation proof from the actual authenticated create response. Recheck live owner/context/deadlines immediately before the permitted request; commit/request-budget uncertainty stops, never retries. No transaction/DB lock across DNS, HTTP or decode. The final-check-to-network race remains unavoidable; a late change cannot produce an association.
- A future request must explicitly omit Authorization/Proxy-Authorization, cookies, referrer and caller headers. No credential/client-certificate discovery or ambient proxy configuration. Use an isolated client without shared browser/cookie/credential state. Request only the selected primary URL, not Location or maximum URL.
- Resolve only the exact approved host through an explicitly chosen bounded resolver. Validate all returned A/AAAA addresses using a reviewed public-unicast/special-purpose-address policy, including IPv4-mapped IPv6; reject private, loopback, link-local, unspecified, multicast, reserved/special-use and mixed acceptable/unacceptable answers. An exhaustive classifier and its data/version are an implementation gate, not supplied by a hostname allowlist.
- Select one validated address, pin the connection to it without a second lookup, and verify actual peer address and TLS hostname **before any HTTP request bytes**. Keep Host/SNI/TLS certificate verification on the exact approved DNS name, normal trust enabled. No automatic alternate-address/Happy-Eyeballs retry, pooled/coalesced connection, DNS fallback or proxy escape. DNS/connection failures stop. No DNS was performed in this review.
- Disable redirects, including same-host redirects; no credential challenge response, HEAD probe, fallback, retry or getImage. Non-200, TLS/host/peer mismatch, duplicate/ambiguous headers, trailers, informational/upgrade responses or uncertainty stop the verification without releasing the upload fences.

### Resource, time and expiry budgets

- Proposed trial budgets: 16 KiB aggregate response headers, at most 128 header pairs, 1 MiB response body, identity content encoding only, and 10 seconds total including resolution/connect/TLS/body. Use smaller sub-deadlines within that total, not additive extensions. These are application choices, not provider maxima. Bound streaming bytes before allocation/copy; never trust Content-Length alone.
- Admit only independently sniffed, MIME-consistent static PNG/JPEG through the reviewed bounded image decoder: at most 4,096 per side/16,777,216 pixels, no animation/multipage/decompression expansion beyond bounds. Bound both HTTP and decode/native memory. Keep the existing two-operation, no-queue, settlement-aware capacity model; abort/timeout does not release capacity until sockets and started native work actually settle.
- Proposed URL residence/use window: at most **30 seconds after create response**, further shortened by review/session/context deadlines and parsed expiration minus **60 seconds**. Missing/malformed/past/insufficient expiration refuses the request. Do not extend a deadline, refresh credentials, trust query expiry claims or wait and retry. A 30-day-looking UTC date does not guarantee even 30 seconds of availability.
- Verification separates response provenance, URL syntax/egress, anonymous byte retrieval, successful bounded decode and recognizable generated-image content. EPS can recompress/convert; source, exported derivative and downloaded-byte digests are separate identities. Exact-byte equality is not a substitute for a reviewed visual criterion. No public/persistent downloaded artifact or automatic usable association follows from a successful decode.
- Consume any permitted verification action once; preserve cancellation/late/error/uncertain evidence without new request permission. Operation restart loses the URL and cannot resume. Review whether a bounded durable verification intent/outcome is needed for crash-safe accounting; it must contain no full URL or query and cannot be smuggled into the existing capture schema.

## Remaining evidence and the single next task

Unknown: actual raw URL syntax/serialization, acceptance of the proposed raw policy, anonymous retrieval/TLS/redirect behavior, returned MIME/bytes/visual content, actual expiry availability, every legitimate path/query variant, Location identity/ID grammar, Inventory ingestion, provider limits, lost-response recovery and remote erasure. Query parameter names/signing semantics are **not required** for B's bounded trial; do not turn them into an unnecessary support dependency.

**Single recommended next task, requiring separate authorization:** implement and independently review an **offline-only operation-local URL/egress policy prototype with synthetic fixtures**, with no production wiring, provider requests, persistence/admission changes or Inventory changes. Prove exact request-target preservation, positive/negative raw syntax, origin/port rules, simulated DNS/peer/TLS mismatch and rebinding, zero credentials/redirect/retry, cancellation/expiry/settlement bounds, one-use proof isolation and log redaction. Tests use invented values/mocked resolution and request seams only. This resolves the enforceability questions before any live budget is considered.

The smallest later way to obtain missing **retrieval** evidence is a separately reviewed and explicitly authorized fresh-response diagnostic: distinct approved generated content where fences require it, one new create response held only in memory, and at most one anonymous primary-image GET. The old 3/3 budget is exhausted. This is not permission for either request. If OAuth prerequisites need exchange/GetUser, those need their own explicit ceiling; otherwise do not add them or refresh. Stop rather than re-POST original content, reconstruct an old URL, request maximum/Location/getImage, follow a redirect or retry. No broad support exchange is the default next step.

One such result could establish only that one URL returned recognizable image bytes under those conditions. It would not establish a universal eBay validator, every query variant, usable Inventory association, recovery, erasure or permission for normal transport. Preserve the original unknown attempt, both fences, its report and existing private review/disposition deadlines regardless of this document or any future diagnostic.
