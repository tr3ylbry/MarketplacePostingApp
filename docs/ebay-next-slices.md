# Proposed eBay Stage 9B slices after seller readiness

Design only, reviewed 2026-11-09. Neither slice is implemented or authorized for real provider writes. Review and separately approve the seller-readiness PR before opening another implementation branch. Stage 9B remains in progress. No `publishOffer`, remote content synchronization, seller-account mutation or Production gateway belongs in either slice.

## Separate future PR: private Blob bytes to EPS

Use a dedicated server-side media boundary, not Reverb's signed-URL ingestion. An owner-scoped request identifies listing/image IDs; the repository derives the trusted durable Blob pathname. Before reading bytes, durably retain the source through the bounded transfer window plus margin using the existing storage lifecycle. Commit first; Blob and eBay I/O run outside transactions. Local removal remains immediate while physical cleanup respects retention. Browser image reads remain unchanged.

The [Media v1_beta.5.0 OpenAPI](https://developer.ebay.com/api-docs/master/commerce/media/openapi/3/commerce_media_v1_beta_oas3.json) describes `POST /commerce/media/v1_beta/image/create_image_from_file`, multipart field `image`, seller `sell.inventory` permission, a 201 response and `Location` image-resource identity. Follow with fixed-host `GET /commerce/media/v1_beta/image/{image_id}` for EPS URL/expiration; expired images return 404. All POSTs have a short limit of 50 requests/5 seconds/user. No image DELETE or idempotency-key operation is documented.

**Sandbox availability gate:** the downloaded image contract lists Production hosts (`apim`, `api`, `apiz`), and the [Media overview](https://developer.ebay.com/api-docs/commerce/media/static/overview.html) warns that Sandbox data may be static/mocked. These do not prove that a particular Sandbox image-upload host transfers real bytes. Confirm the image-specific Sandbox host and usable create/readback behavior through current official documentation or developer support before enabling any real transfer. Never substitute a Production host or the deprecated Trading picture-upload operation. No upload or authenticated probe was made during this design review.

The [official image guide](https://www.developer.ebay.com/api-docs/sell/static/inventory/managing-image-media.html) supports JPG/GIF/PNG/BMP/TIFF/AVIF/HEIC/WEBP, but excludes animation/multipage behavior. Its 12 MB and 15,000 combined-dimension figures are illustrative limits, not a hard universal contract. Before implementation, resolve current exact byte/dimension minima/maxima against the picture policy, supported categories and Sandbox. Proposed initial product subset: verified static JPEG/PNG only, within the existing app upload cap and stricter confirmed limits; no automatic HEIC conversion or new dependency without review. Inspect magic bytes, decoded dimensions/pixel budget, declared and actual length/MIME, and reject decompression bombs/unsupported formats before upload. Listing photo count/order must remain deterministic.

Proposed orchestration and persistence:

1. Explicit review binds owner, environment, verified seller/connection version, listing/image version and ordered image identities. No browser pathname/URL authority.
2. Short transaction stores an attempt with source content digest and durable upload fence, extends source retention and claims one bounded lease. Use seller/environment/image/digest to reuse a confirmed unexpired association; never deduplicate across owners/sellers.
3. Bounded private byte read/validated multipart stream to a pinned, verified Sandbox host; cancellation closes streams. Bound total memory if the HTTP library buffers multipart. Do not persist or expose a temporary Blob capability.
4. Capture validated provider image ID immediately; never follow arbitrary `Location`. GET that exact resource, validate HTTPS EPS host/path and expiration, and persist only an allowlisted source-image → EPS association with order, digest, seller/environment and expiry.
5. Revalidate connection/listing/image versions before acknowledging success. An orphaned successful provider upload still receives a durable residual record; local parent deletion must not erase evidence needed for reconciliation.

Failure/reconciliation: before the POST, persist that it may be transmitted. Timeout/5xx or loss of the 201 identity becomes **unknown**, not a blind second POST. If a trustworthy resource ID was captured, reconcile using GET; a content digest alone cannot recover an unknown eBay image ID. Without documented provider idempotency/search, require manual resolution or an explicitly approved duplicate-risk retry. Do not invent successful deletion or promise immediate erasure. A known unused EPS copy has provider-controlled expiration; an active listing can extend it. Releasing local associations/source retention does not retract remote bytes. Keep minimal residual identity/expiry evidence without retaining source signed URLs. Reuse only same-seller, unexpired, content-matching images.

Test plan: fake multipart byte/order inspection; foreign-owner denial; source removed during transfer; expiration/reuse; false MIME and oversized dimensions; bounded streams; hostile Location/EPS URLs; 401/403/429/5xx/timeout; unknown outcome without repost; connection/version races; no tokens/URLs in logs or browser storage; ledger survival after local deletion; no transactions around network calls. Separate real approval must name one/two generated images, exact Sandbox seller, scope upgrade, maximum POST count, readback evidence and residual-copy/expiration limitation. Prove actual ingested pixels rather than accepting a canned 200. No inventory attachment is needed for that acceptance. Cleanup must remove only disposable local/Blob data after retention and document any EPS residual until verified expiry.

## Separate future PR: guarded Inventory Item staging

The [Inventory v1.18.5 OpenAPI](https://developer.ebay.com/api-docs/master/sell/inventory/openapi/3/sell_inventory_v1_oas3.json) defines `PUT /sell/inventory/v1/inventory_item/{sku}` as replacement, including effects on associated listings. It requires seller `sell.inventory` permission. This future write grant needs a separate reviewed one-use authorization profile; the read-only profile cannot be silently expanded. GET the exact item first, and enumerate `GET /sell/inventory/v1/offer?sku=...` completely across supported marketplaces/formats. No offer POST/PUT or publication method belongs in this PR.

Keep distinct local Listing ID, deterministic SKU, Inventory Item identity, future Offer ID and eventual published Listing ID. The SKU is immutable identity, not ownership proof. Maintain a durable seller/environment-bound staging record and append-only attempts/tombstones independent of local-listing cascades. A reviewed payload digest/version records which complete replacement was authorized. Canonical Save never triggers PUT; no automatic update endpoint is added initially.

Minimum write/reconciliation design:

1. Explicit preview and confirmation; owner/listing version and verified seller/connection fence, current metadata/condition and approved EPS associations.
2. Fresh exact-item lookup and complete offer enumeration. A pre-existing unproven SKU, any related offer/listing/group, multiple/partial result, account mismatch or unknown earlier attempt blocks writing. Never adopt by prefix or payload similarity alone.
3. Under a short local transaction, claim exclusive owner/seller/SKU attempt lease/version and persist a pre-transmission fence. End transaction before requests. Revalidate immediately before the one PUT.
4. Only a fresh absence with no unresolved earlier attempt may create. An existing item may be touched only with durable prior confirmed app ownership and a new narrowly reviewed update policy; initial staging can simply refuse replacements. Provider absence checks do not reserve a SKU against another client. eBay's contract supplies no assumed conditional-create/ETag guarantee: this residual race needs explicit design/owner review before real PUT. If strict no-overwrite assurance cannot be established, keep writes blocked rather than pretend local locking covers another eBay client.
5. Verify exact-item readback and all-offer absence, bind the confirmed remote identity/payload to the durable attempt and fence stale results. No `MarketplaceListing` is falsely marked published. Use separate staging state from generic publication status.

Uncertain PUT: preserve `unknown` with the transmitted payload/version and seller. A later explicit GET may reconcile a known attempt but cannot prove ownership solely from a matching SKU/body if another client could have written it. Do not blindly resend full replacement. Changed/foreign content, offers, missing identity evidence or unresolved races require manual resolution. Reconnect/disconnect fences local commits; transmitted provider effects cannot be recalled.

Cleanup is part of this PR, not postponed to Stage 9D. Inventory DELETE can remove offers and published single-variation listings and affect groups. It requires durable confirmed app ownership, exact seller/environment/SKU, a fresh complete no-offers/no-listings/no-group check and separate explicit confirmation. There is no assumed atomic check-and-delete guarantee against outside actors. If that race or group/publication state cannot be excluded safely, refuse automated deletion and provide a precise manual cleanup record. Never delete based only on local-listing deletion or SKU prefix; do not cascade away attempts/tombstones. After one approved DELETE, GET reconciliation distinguishes confirmed absent from unknown; never blindly retry. Local photos and connection remain. Preserve minimal remote residuals until absence is confirmed.

Test plan: fake full PUT replacement semantics; pre-existing SKU collision; seller/environment isolation; published/offer/group refusal; complete pagination across marketplace/format; stale preview and concurrent local attempts; crash before/after send; lost response; no blind second PUT/DELETE; fresh cleanup checks; foreign resource preservation; local parent deletion retains evidence; no network-in-transaction; no Save/navigation writes; browser/log privacy. No real staging until its ownership/race and cleanup design is approved. A later bounded real acceptance must specify one fresh SKU, seller, payload/photos, maximum write count, readback and verified cleanup, with an immediate stop for collisions/uncertainty. Inventory eligibility remains pending until that separately authorized operation; read-only success does not establish it.
