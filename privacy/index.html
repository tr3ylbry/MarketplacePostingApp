MarketplacePostingApp

Development Privacy Notice

Last updated November 20, 2026.

Scope and current operation

MarketplacePostingApp is a development project for organizing items, storing private listing photos, previewing marketplace formats and explicitly managing Reverb drafts. The application runs locally, with PostgreSQL storage and external authentication, image-storage and marketplace services. Development testing uses GitHub authentication, a development Vercel Private Blob store, Reverb Sandbox and eBay Sandbox. Implemented eBay features include seller authorization, explicit read-only metadata and seller-readiness checks, and local private-photo preparation. A separate manual diagnostic tool supports transfer of one newly generated test image and one anonymous primary-image retrieval for visual comparison against the exact submitted export. Each run requires separate approval of its reviewed code, content and request budget. This tool is separate from ordinary application workflows; diagnostic retrieval and comparison have synthetic/local evidence until separately authorized real acceptance is recorded. The application is not publicly deployed.

Information used and why

  • Sign-in and sessions: GitHub account identifiers, name, email and avatar information identify the user and support owner-authorized access. Better Auth stores provider account records, encrypted OAuth tokens where applicable, and database-backed sessions. Session records may include IP address and browser information.
  • Items and photos: entered titles, descriptions, prices, item attributes, marketplace preferences and publication history support inventory and draft workflows. Image bytes and metadata, including original filenames, file types, size and order, support uploads and private viewing. Private originals are preserved. The reviewed server-only derivative workflow produces and verifies a separate export copy with supported identifying metadata removed and visual orientation preserved; ordinary upload and private viewing do not sanitize the original. This does not remove identifying information visible or hidden in pixels. The controlled eBay experiment uses a newly generated non-personal image; avoid uploading personal or location-sensitive photos for testing.
  • Reverb connections and actions: an encrypted Personal Access Token, shop identity, environment and connection timestamps support explicit provider requests. Draft reviews, attempt records and remote listing IDs/status help reconcile actions and avoid unsafe duplicate requests.
  • eBay Sandbox connections: when explicitly authorized, the connection flow processes an authorization code on the server and stores encrypted access/refresh tokens, granted permissions, expiry times, a hashed stable seller identifier and a seller username label. Hashed one-use authorization state and session/configuration bindings protect the callback. Authorization codes and raw seller profiles are not retained as application records; limited state validity does not guarantee immediate deletion of expired records.
  • Controlled media evidence: owner-bound attempt records retain hashed seller, session, action and source/final-content identities, versions, timing and uncertainty fences to prevent unsafe duplicate sends. Separate bounded append-only reports retain response status, field types, URL structure and independently valid expiry facts. Reports exclude whole returned URLs, resource IDs, URL query values, raw response bodies, private storage paths, filenames, image bytes and credentials. For a separately approved diagnostic retrieval, append-only records retain bounded request, outcome and settlement facts. Generated-image visual results and scores may be recorded in a bounded private acceptance report, not those database envelopes. A captured response, retrieved image or visual match does not establish an associated image, remote ownership or permission to send again.

Storage and third-party services

PostgreSQL holds application records; Vercel Private Blob holds uploaded image bytes. GitHub handles authentication. Explicit Reverb draft creation sends selected listing content and temporary private photo access to Reverb, which can retain its own copies. Ordinary local saves and page navigation do not automatically push listing content to Reverb. Explicit eBay Sandbox connection actions use eBay for seller consent, server-side token exchange, authenticated identity checks and supported connection token renewal. Explicit preparation can read seller settings and metadata. A separately approved manual discovery may send one newly generated image through the reviewed private-source and derivative workflow to eBay Sandbox. eBay may resize, compress or convert it and retain an independent copy. A separately approved diagnostic run may retrieve the fresh primary image once without seller credentials, cookies or referrer for bounded comparison against the exact submitted export. The returned URL and its opaque query remain temporarily in operation-local memory and are not put in logs or durable storage. Token refresh, provider retries and other follow-up requests are not permitted. Inventory, offers and listings are not sent.

These providers process information involved in their services under their own policies. This notice describes the application, not a guarantee about provider retention or operations. This public notice is a static GitHub Pages page, separate from the application and database. It contains no analytics scripts, tracking pixels, forms or application authentication. GitHub Pages records visitor IP addresses for security purposes, as described in GitHub's hosting documentation.

eBay Sandbox connections, preparation and controlled discovery

The local-development connection uses Sandbox authorization-code OAuth and authenticated read-only Trading GetUser identity checks. Seller identity is derived on the server; browser-entered identifiers and mocked identity responses are not seller proof. Sandbox connection and preparation workflows have been tested, with remaining provider coverage documented separately. Opening settings or preparation pages and ordinary local saves do not initiate eBay requests.

The manual image experiment requires separately explicit consent to the base eBay scope plus sell.inventory. That provider grant is broader than image creation and can permit Inventory and Offer writes at eBay; the application continues to disable those writes. Successful media consent replaces the existing read-only readiness permissions, so later readiness use requires a separate explicit authorization. Each diagnostic run needs an explicitly approved ceiling of at most one code exchange, one GetUser identity check, one image-create request and one anonymous primary-image retrieval, including failed requests. A smaller budget needs its own explicit approval; skipped or failed steps never authorize retries or alternate requests. Token refresh and provider retries are not permitted. Normal EPS transport and real receipt/association admission, Inventory/Offer/Listing writes, business-policy or location creation, background synchronization, Production sellers and public application deployment remain unavailable. Returned URL shapes or expiry are observations and do not prove trusted download, successful ingestion or remote deletion.

Security and browser data

The server checks authenticated ownership before accessing listings, connections or images. Reverb credentials and the eBay connection flow's access/refresh tokens are encrypted server-side under separate keys; GitHub OAuth token encryption is configured through Better Auth. This does not mean every database field is encrypted, and encryption cannot protect data if the running server or its keys are compromised.

Session cookies are HttpOnly and SameSite=Lax; Secure cookies are used on HTTPS origins. The eBay connection workflow requires trusted HTTPS on loopback. Other local-development workflows may use HTTP only on loopback with matching authentication configuration. Provider credentials and signed photo URLs are not persisted in browser localStorage/sessionStorage or intentionally written to application logs. Temporary image URLs are bearer access: anyone receiving a valid URL can use it until expiry, and downloaded copies cannot be recalled.

Older local listings may remain in browser storage. Import is an explicit action and does not delete that original browser data. PostgreSQL is the source of truth for normal current use.

Disconnection and deletion

Signing out ends the current application session; it does not erase account or listing records or revoke provider authorization. Reverb disconnection removes the local stored connection, not the provider's token or remote drafts, and cannot cancel a request already in flight. GitHub and Reverb authorizations can be managed or revoked through those providers. eBay disconnection clears locally stored OAuth tokens and pending authorization state while retaining a minimal versioned connection record to reject stale in-flight results; it does not revoke eBay consent or erase eBay-held data. Manage or revoke eBay authorization separately through eBay.

Deleting a local listing removes it from the product and queues eligible photo cleanup. Minimum consumed-action and uncertain-outcome safety history is retained; listing or connection deletion does not release a committed media fence or make the same content safe to send again. Local deletion does not automatically delete a remote Reverb draft. Remote draft deletion is a separate explicit action; it leaves the local item and photos intact. Removing a local photo does not erase copies already downloaded by a provider or recipient. The capture tool provides no remote eBay image deletion or reliable lost-response recovery; a remote image may remain even when local cleanup completes or a returned expiry passes.

Retention and limits

There is no fixed automatic account-data deletion schedule or complete self-service account-erasure interface. Development records remain until removed or cleaned up. Privacy/deletion requests require review by the project maintainer; deletion timing and scope depend on the records, service and available controls. No immediate or complete erasure guarantee is made.

Removing an image or listing hides it from the application immediately, but physical image deletion may be delayed. Photos shared for Reverb ingestion remain protected for at least the issued 15-minute capability lifetime plus a one-minute safety margin. A durable cleanup ledger and operator-run cleanup handle deferred objects and retries; physical deletion may occur later if cleanup has not run or a provider operation fails. Local deletion does not establish deletion from independent provider copies or any separately maintained backups.

The controlled diagnostic protects its private source for at least six minutes, or an existing longer hold, before storage work. Removing the disposable listing or photo can therefore defer physical cleanup. Capture and diagnostic reports and minimum action/content-fence history have no automatic purge, renewal or hold-release feature. Their retention and any offboarding request require private maintainer review. Removing identifying safety history may require additional engineering and disabling the affected mutation capability first; erased history must not reopen an unsafe namespace. No immediate local or remote erasure guarantee is made.
